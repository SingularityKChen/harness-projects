# 切片栈（C）ExecPlan

> 状态：Active
> 创建：2026-09-20
> 范围：让 MVP-0 的纵向链路在无凭据、无网络的条件下跑通，并让它的进度断言从"因正确原因失败"变成"全绿"。包含 core、controller、client 三个包与测试层的组合根。
> 上游输入：`AGENTS.md`、`PLANS.md`、`docs/exec-plan/active/2026-09-20-mvp0-parallel-stacks.md`（控制计划）、`docs/exec-plan/active/2026-09-20-contract-plane.md`（本栈依赖的契约）

## Purpose / Big Picture

完成后，一条链路走完并且**每一步都可被断言**：

```text
工作区 → 规划条目 → 工作项 → 开始工作 → 执行上下文 → 分支/提交 → 变更请求 → CI
```

判定方式是 `node --test tests/mvp0` 全绿，且它在 `pnpm verify` 内。过程中规划状态始终由规划 provider 拥有：CI 失败、执行完成、合并都不会改写它；任何未被 provider 确认的写入都不会被报告为"已保存"。

## Context and Orientation

### 术语

| 词 | 意思 |
|---|---|
| 组合根 | 把 core 与具体 provider 装配起来的唯一位置。本栈把它放在测试层，因为包边界矩阵不允许生产包同时 import `core` 与 `providers/*` |
| 进度轨道 | `tests/mvp0/`，一条**故意允许失败**的端到端断言；它不进入必需门禁，直到本栈最后一个批次让它变绿 |
| 执行上下文 | 规划进入工程的显式桥：工作项 + 仓库 → 工作树 + 分支 + 可选执行会话 |
| 状态策略 | `source_managed` / `harness_managed` / `manual`；它决定工程事件能否影响规划状态，默认不能 |
| 降级 | 某个 provider 不可用时，链路只在局部失败：读侧给最后已知值，写侧被拒绝并说明恢复动作 |

### 当前事实（本栈开始前）

- `packages/core`、`packages/controller`、`packages/client` 都只有 `packageId` 常量。
- 契约栈（A）已提供：领域模型、五域 port、离线替身（含 Storage 内存替身）、契约套件。
- 迁移运行器（B1）已存在，但**本栈不使用它**：SQLite 业务表属 #27/#28，受 Gate E1 约束。
- `package.json` 的 `test` 脚本运行 `tests/contract tests/integration tests/e2e`；`tests/mvp0` 由新增的 `test:mvp0` 脚本单独运行。

### 为什么先有一条会失败的断言

issue #42 的判据是"用例存在，且失败信息指向哪个节点还没有实现"，并明确禁止 skip（skip 不产生压力）。本栈把它落成 `tests/mvp0/` 轨道：每个节点一条断言，未实现时失败信息点名节点；每完成一个批次，失败断言数单调下降。批次 C5 让它全绿并把它提升进 `pnpm verify`。

## Design / Spec

### D1. core 只认识 port，不认识 provider

`packages/core` 的依赖只有 `capabilities` 与 `domain`。所有 provider 通过构造函数注入；core 内部没有任何 `if (provider === 'github')` 形态的分支，只有 capability key。组合发生在测试层。

### D2. 观察是唯一入口

外部世界的变化只有一条路径进入系统：

```text
ProviderObservation → 去重 → 顺序守卫 → 事务内 upsert → 关系更新 → 投影重算 → 修订号 +1
```

去重键由 provider 计算并被契约套件固定；顺序守卫比较来源版本，旧观察不得覆盖新观察；重复观察不产生第二个实体——这条是本栈最高优先级的断言（`tests/README.md` §2 第 1、4 类）。

### D3. 写路径的状态机

```text
validating → writing → confirmed | reconciled | unknown | conflict | failed
```

- `confirmed` 需要 provider 确认或 read-after-write 证据；在这之前，调用方只能看到 `saving`。
- `unknown`（例如创建结果在传输中丢失）必须先 reconcile，禁止盲目重试创建。
- `conflict` 保留最后已知权威值与本次尝试值，并提供重新应用与刷新两种恢复动作。
- 写尝试以 `(workspace, idempotency_key)` 去重：同键重放返回原结果。

### D4. Start Work 是补偿序列，不是一次调用

固定顺序：写 pending 执行上下文 → 创建工作树与分支 → 启动执行。每一步都在提交后才做下一步：

| 失败点 | 必须观察到的结果 |
|---|---|
| 工作项或仓库不合法 | 不产生任何执行上下文 |
| 工作树创建失败 | 执行上下文标记失败，**不启动**执行 |
| 执行启动失败 | 执行上下文保留并降级为 `manual_fallback`，工作树与分支仍在 |
| 同一工作项重复开始 | 返回已存在的 active 上下文，不产生第二份工作树或分支 |
| 工作树是脏的 | 不自动清理；清理只在显式请求时进行，且脏工作树必须被拒绝而不是被覆盖 |

### D5. 投影只承载四类内容

查询只返回：权威快照、外部事实的缓存、派生投影、能力与新鲜度元数据。普通查询**不得**隐式触发外部写入。派生值（Attention、Ready to Merge 等）必须带 `derived` 标记，且永不写回外部字段。

### D6. 状态策略与不变量 3

`source_managed` / `harness_managed` / `manual` 三种策略都不得让"CI 失败""执行完成""PR 合并"直接改写规划状态。唯一允许的联动是显式配置的策略加上显式的状态写入命令。这条要在三种策略下各有一条负向测试。

### D7. 被放弃的方案

| 方案 | 为什么放弃 |
|---|---|
| core 内直接 new 出离线 provider 以便跑通 | 会让生产包依赖实现，边界测试会拦下；而且真实 provider 替换时要把装配逻辑从 core 里再剥出来 |
| 让 controller 暴露 provider 原生对象 | 前端会因此依赖平台形状；wire 层只传内部对象 |
| 用 SQLite 落执行上下文 | #27/#28 受 Gate E1 约束；本栈用 Storage 契约的内存替身，验证的是"控制事实被持久化到契约边界"，不是"表长什么样" |
| 进度轨道直接进必需门禁 | 分支保护要求 `PR Fast Gate` 绿；故意失败的断言必须与必需门禁分开，否则红叉会常态化 |
| 一次 PR 交付整个 core | 超过单 PR 体量上限，且失败时无法定位到具体能力 |

## Global Constraints

- 不引入任何运行时依赖（含 uuid 库：用 `node:crypto`）。
- 单文件 ≤ 200 行，单函数 ≤ 40 行。
- core / controller / client 不得 import 任何 provider 或 storage 实现；边界测试必须保持绿。
- `client` 不得 import React，也不得访问外部平台。
- 所有断言在无凭据、无网络条件下通过。
- 只允许 rebase merge；不自行合并 PR。

## Surprises & Discoveries

- **Observation**：`.github/workflows/ci.yml` 的触发条件是 `pull_request: branches: [main]`，因此**栈内 PR（base 不是 `main`）不会跑 `PR Fast Gate`**——本轮只有 #80 拿到了真实 CI 证据，其余八个只有 advisory 的 `Issue policy`。
  **Evidence**：`gh pr checks <n>` 在 #80 上返回 Disclosure scan / Issue policy / PR Fast Gate 三个检查，在其余八个上只返回 Issue policy。
  **Decision impact**：栈内批次必须自带本地等价证据（`tsc --noEmit` + 完整 `node --test`），并在合并前逐分支复跑；这一条已写进 `docs/project-management/merge-queue.md` §4.2。把 CI 触发分支扩展到 `**` 是另一个批次，需要同步 `docs/development/ci.yml` 与 `scripts/workflow-check.mjs`。

- **Observation**：base 不是 `main` 的 PR 不会生成 `closingIssuesReferences`，即使描述里写了 `Closes #N`。
  **Evidence**：`gh pr view 81 --json closingIssuesReferences` → `[]`；`gh pr view 80 …` → `[74]`。
  **Decision impact**：栈内 PR 的 issue 关联靠描述与队列文档核对；GitHub 会在下层分支合并后被删除时把上层 PR 的 base 重定向到 `main`，届时 closing 关联才生效——此事必须在下一次合并后回读确认。

（实现期间如实记录。实现者必须把"哪条断言在哪一层失败"与"为什么失败"分开写，避免用"调整断言"掩盖真实缺陷。）

## Idempotence and Recovery

- 全部验证命令只读且可重复。
- 内存替身没有外部副作用，失败后重跑即可；不需要清理数据库或目录。
- 若某个断言在当前 head 上不可能通过（例如依赖尚未落地），必须把它写成"点名未实现节点"的失败，而不是 skip 或注释掉。
- 分支已推送后改写需先建恢复锚点并用精确 lease 强推。
