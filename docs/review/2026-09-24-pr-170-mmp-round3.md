## 评审方法与边界

- **流程**：先锁定 head/base、全部 thread 与 checks → 按栈序在一次性 clone 里逐合并点跑门禁（并集先于逐 PR）→ 6 个逐层子评审加 1 个跨层子评审并行取证，都只读，用 Opus（任务需要对 schema、事务并发和文档时点事实做对抗性推理）→ 主控独立复现每一条阻塞级结论，并裁定级别 → 74 条 inline 连同 6 份总结一次性提交。
- **复评原则**：上一轮每条意见都在当前 head 上复跑反例或变异，thread 的 resolve 状态和作者回复都不当作证据。每次变异都先打印被改的那一行，证明变异确实生效，还原后再复跑一次确认回绿。
- **主控对子评审定级的调整**：报成 P1、被降为 P2 的有三条——#157 跨工作区作用域（base 上同样复现，根因在 `main` 的端口）、#157 账本键（本层合并点没有写者）、#175 `Closes #5`（验收在端口层字面成立，缺口是没有 issue 跟踪）。另有一条报成 P1、按上一轮口径维持 P2 的：#121 #119 验收 1 的墙钟时间（没有新事实）。#122 验收 3 那条，主控一度考虑降级，但 #27 Scope 要求把不变量编码进数据库，最终维持 P1。
- **边界**：没有重跑沙箱实验（那会写外部仓库）；CI 只读了 conclusions，没有打开日志；看板字段没有代写（上一轮手动写 `Changes requested` 与投影不一致，被观察者报成漂移）。子评审的实验脚本留在一次性 clone 里，没有进仓库。
