## 分层检查

### 代码与状态语义

- `startRun` 先检查 offline、binding/objectKind，再检查 `startUnavailable`，成功时生成 `manual-run:` ref 并进行 round-trip 校验（`index.ts:194-210`）。
- `getRun`/`cancelRun` 从 ref 派生状态且重新构造返回 ref，不回显调用方对象；这一点与 port 注释和契约用例一致。
- `cancelRun` 先能力后身份，能力关闭时对外来/畸形 ref 应答 `not_supported`；当前实现与共享 contract suite 一致。
- 关键缺陷不在 provider 局部函数，而在 provider identity 没有进入 core Storage；纯函数 ref 不能弥补系统事实缺失。

### 产品闭环

成功切片（provider 已绑定）可得到真实本地 Git 工作树/分支、`ready` context、`running` run；集成测试还验证了 provider 不直接写 Storage、重启后运行记录字段保持。

失败切片只得到 `ready + manual_fallback + failed run`，没有人工 provider 运行。该结果与“保留环境”一致，但与“人工执行会话可见且可推进”不一致。PR 自身已将其归因到 #171；该边界必须进入 MMP 验收表，不能用 `manual_fallback` 字符串替代一等运行。

### 架构边界与 Storage 权威

Provider 不写 Storage、core 的 `recordRun` 是唯一运行记录写入入口，符合单一事实源原则；但当前 Storage schema 没有 provider external identity，导致 provider 状态无法成为可持续的工程事实。#172 不是纯 provider 修复，应包含 capabilities、fake storage、SQLite migration、core projection/query 与重启/取消集成证据。

### 测试与反例

已有 27 条 execution contract、4 条人工 provider integration、全仓 contract/integration/e2e 与 boundary checks 在 PR body/Checks 中为绿；这些证明局部契约和真实 Git 组装，不证明产品入口闭环。已有判别性用例覆盖了返回 ref 重建、能力先于身份、round-trip、重复工作树与重启边界的“引用丢失”事实。

仍需上层补两类判别性反例：

1. Harness provider `startRun` 失败后，core 是否真正调用人工 provider 并把同一 context 的 run 变为 `running`；重试、重启、换实例后是否可查询/取消。
2. SQLite（而非 fake Storage）持久化 external identity 后，重启读取是否可路由到正确 binding；不存在/伪造/错误 binding 的 ref 是否 fail closed。
