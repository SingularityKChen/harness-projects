## 分层审查

### 代码与信任边界

- Git 调用集中在 `git-runner.ts`，通过 `execFile` 接收 argv；源码扫描测试通过。
- `createWorktree` 的路径守卫顺序是字符串拒绝、canonicalize、允许根 symlink 检查、目标 ancestor symlink 检查、根内判定，之后才调用 Git。当前已覆盖根本身和已有 ancestor 两类 symlink 形态。
- `firstLink` 的当前调用 `firstLink(target.ancestor, candidate)` 在 `target.ancestor` 是 symlink 的场景已经由 `canonicalize` 返回的 ancestor 自身检查补齐；这正是旧 P1 的根因修复。
- `reuseBlockedBy` 通过目标工作树自己的 `git -C` 读回 common-dir、git-dir 和 HEAD，避免把登记账本当作可复用事实。

### 产品闭环

本 PR 交付的是本地 Git provider 自身的 repository read、branch create、worktree create 子集；#209 负责把它接进 core `provisionGit/startWork` 的纵向闭环。当前 provider 测试可以证明“拒绝时不写、成功后能读回、重复请求不重复建”，不能单独证明 Start Work 在重启、ready-context 重查和关系投影上的系统行为。

因此，#212（工作树 read 能力）、#211（ready context 重查）、#213（core 基线未知不得猜测）、#214（默认落点移到检出之外）必须继续作为 stack 后续 issue 读取和复评，不能由 #160 的 provider 绿测试代替。

### 架构边界

provider 仅依赖 capabilities/domain，Git 进程边界在 provider 内；没有发现 provider import core、ui 或 storage 的反向依赖。能力快照只声明 repository read、branch create、worktree create；本层不声明 worktree remove，符合 #138 分层。

### 测试判别力与反例

当前 provider 集成测试：24/24；源码 argv 契约：1/1；边界契约：7/7。完整 integration + e2e：132/132（当前 worktree 的测试输出）。关键变异已验证 ancestor guard、默认根 symlink、占用路径、prunable 登记、大小写变体、写后回读等行为。

仍缺少的判别性测试是“只让 `symbolic-ref` 或 `config --get` 失败”的读错误交错。已有 `faultRunner({ offline: true })` 让所有 Git 命令失败，不能证明 `baseBranch()` 对中途非 `not_found` 错误正确传播；这正是 P2 的机制缺口。
