## 4. 反例和根因核查

### 4.1 关系目标身份（P2，当前未解决）

当前恢复测试：

```js
assert.equal(hasWorktree.length, 1)
assert.equal(new Set(hasWorktree.map((relation) => relation.to)).size, 1)
```

这只证明有一条关系且目标不分叉；若唯一关系指向错误 worktree entity，仍会通过。生产代码的确定性身份定义在 `packages/core/src/chain-facts.ts:47`：

```js
worktreeEntityId(workspaceId, repositoryId, workItemId)
```

建议在当前测试中直接断言：

```js
assert.equal(
  hasWorktree[0].to,
  worktreeEntityId(workspaceId, REPOSITORY_ID, request.workItemId),
)
```

独立变异证据：在当前 head 的 Storage `putRelation` 前把 `to` 改成 `worktree-mutated-target`，真实 `startWork` 仍返回 `ready`，而恢复断言所使用的两个值仍为 `relationCount=1`、`uniqueTargets=1`；唯一目标实际是错误实体 `worktree-mutated-target`。因此现有断言确实观察不到目标身份变异。此项是 P2，不阻塞本 PR。

### 4.2 #211 stale-ready 验收仍不完整

当前生产代码 `packages/core/src/start-work.ts:230-271` 已在 ready context 上调用 Development worktree read-back，并在 provider 不确认时把上下文置为 Failed；当前真实 Git 用例 `tests/integration/local-git-core-provisioning.test.js:168-180` 验证了 `git worktree remove --force` 加 `git branch -D` 后不会继续返回 confirmed。

#211 的验收还要求“删除目录但留下 prunable 登记”的变体，以及完整 worktree/branch intact 时不新建资源。当前 PR 的真实 Git 用例没有这两条判别测试；因此 #211 仍应保持 OPEN 或由独立修复/补测收口。这个缺口不应被 CI 全绿掩盖。

### 4.3 #200 / #212 的 fake contract 缺口

当前 `packages/providers/fake/src/development.ts:167-174` 的 `createWorktree` 仍只按 path ref 判定 conflict，不比较 branch；同路径但不同分支仍可返回 `conflict`。#200 明确要求该情形结构化硬失败，shared Development suite 也应加入判别用例。当前 #209 新增 `getWorktree` 和 core conflict read-back 后，core 能把分支不匹配转成失败，但 provider 契约本身仍不满足 #200 的验收。归类为 P2，保持 issue 追踪，不把它误报为本 PR 已闭合。

### 4.4 #207 及产品边界

#207 的供应路径验收在当前 8 条真实 Git core 测试中大部分成立：分支/工作树落盘、重试不复制、恢复状态、不可复用登记拒绝、非 main 基线和 ready stale 反例均有证据。但：

- #207 的“never produces ready”字面范围在 existing ready context 上曾有反例，当前实现只覆盖部分路径，故保持 `Refs #207`；
- `recordStartFacts` 在工作树步骤失败时仍可能用 branch 兜底写 `has_worktree`，对应 #192，不能由本 PR 的 ready/confirmed 断言替代；
- 非测试代码尚无宿主将 local Git provider 装配到用户入口的证据，#132/#142 仍是 MMP 产品闭环缺口；
- 默认工作树根仍在检出内，#214 是已登记的后续产品/安全边界决策；#160 当前防线不能被本 PR 的测试覆盖替代。
