## 分层结论

### 代码与状态

provider 的 `startRun` / `getRun` / `cancelRun` 采用稳定 ref 派生，返回值重新构造，能力检查先于身份检查；round-trip、伪造形状边界、坏时钟和冻结配置都有判别性用例。core 现在在 primary run 与 fallback run 成功后都把 provider ref 交给 `recordRun`，query/replay 从 Storage 回填 `runExternalId`。当前没有发现新的错误吞噬或权威 `Saved` 越权。

### 产品闭环

显式组装 primary + fallback 时，失败路径可以产生 `manual_fallback` 的 running run；只有 primary provider 失败并且 fallback provider ack 才写 `running/providerRef`，符合“先 ack 后权威状态”的仓库不变量。真实宿主仍无该组合根，且失败后的取消/轮询没有 core command，因此这仍是库级交付，不是用户可观察的完整 Start Work 产品闭环。

### 架构边界

provider 没有直接 import Storage；Storage 是唯一 run record 写者；SQLite migration 004 通过显式清单接入，依赖方向与 boundaries 通过。新增 fallback provider 是 core registry 的能力解析扩展，未引入 provider 间互调。

### 测试与反例

CI 与本地全量测试均绿，但测试不能替代产品闭环。最明显的证据缺口是 SQLite providerRef round-trip 没进入正式用例，且 fallback 状态契约没有“非 running 成功响应”的反例；这两项应在后续 issue/验收中补齐。

- #139：OPEN。当前 PR 只完成 provider + run identity 机制，需由 #172/宿主 MMP gate 决定何时勾选“重启后读回人工运行”。
