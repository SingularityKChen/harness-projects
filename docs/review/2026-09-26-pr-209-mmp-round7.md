## 4. 反例与系统级闭环复核

### 4.1 已 `ready` 上下文的陈旧工作树反例（系统级 P1，非本 PR 引入）

使用当前 head 的真实临时仓库复现：

```text
startWork(k1) -> ready / confirmed=true，工作树和 work/probe-ready 在盘上
git worktree remove <repo>/.worktrees/probe-ready
git branch -D work/probe-ready
startWork(k2) -> ready / writeState=saved / confirmed=true
磁盘 -> 只有主检出，没有工作树，也没有 work/probe-ready
```

复现命令使用 `tests/integration/local-git-fixture.js` 的 `makeFixture`、`coreContextFor`、真实 `git` runner；当前 head 的输出为第二次 `status=ready`、`writeState=saved`、`confirmed=true`。原因是 `claimContext -> existing -> reportForExisting(Ready)` 不再问 provider。该行为违反 `AGENTS.md` §1.1 的 Provider ack / reconcile 硬约束，已在 #211 记录，不能归咎于 #209 的测试改动。#209 已如实把声明收窄为“供应路径上不得报 ready”。

### 4.2 重试、恢复与磁盘事实

当前测试已覆盖并实际通过：

- 同一请求重试后工作树总数为主检出 + 1，工作分支总数为 1；两个句柄规范化后指向同一工作树。
- 恢复用例必须得到 `ready`、`confirmed=true`、字符串句柄，并回读工作树路径、句柄指向和 `refs/heads/work/*` 总数。
- 目录消失、`.git` 被删、目录被替换为独立仓库、lock 后被替换均在供应路径返回 `invalid_input`，不报 `ready`。
- 分支已被别处检出时 core 不报成功；非 `main` 且无 `origin/HEAD` 的 `trunk` 仓库可供应。

这些是有判别力的系统证据，但不覆盖已 `ready` 记录复用时的 provider 复核，也不证明宿主已把该 provider 接入用户入口。

### 4.3 关系身份的精度缺口（P2 候选）

`恢复供应` 当前断言：

```js
hasWorktree.length === 1
new Set(hasWorktree.map((relation) => relation.to)).size === 1
```

这能证明没有第二条关系，但若实现把唯一关系指向错误的 worktree entity，仍可通过。建议补充：

```js
assert.equal(
  hasWorktree[0].to,
  worktreeEntityId(workspaceId, REPOSITORY_ID, 'wi-165'),
  '关系必须指向 (workspace, repository, workItem) 的确定性实体身份',
)
```

这是精确性增强，现有 `tests/integration/start-work-retry-identity.test.js` 已有离线覆盖，因此不作为本 PR 的 P1。
