# ADR-0004：结果不确定的外部创建先对账再重试；没有自然键时它是产品可见状态

> 状态：Proposed
> 日期：2026-09-21
> 来源：`docs/exec-plan/completed/2026-09-21-gate-e1-ruling.md`（Batch 1，issue #25）；证据见 `docs/architecture/gate-e1-write-and-events.md`（E1-3 / #24）
> 订正：2026-09-23（L1 / #119）——本 ADR 的证据边界与结论句按 `docs/architecture/gate-e1-uncertain-create.md` 的实测就地订正，原文保留

## Decision

1. 任何外部创建/挂接写入在发起前，把**不依赖响应的自然键**持久化到 `pending_external_write`；对"把既有内容加入项目"这一步，幂等键是 `(project, content_id)`，其中 `content_id` 是发起方本来就持有的输入。
2. 响应丢失时**先对账**：重读条目集合，按自然键查找既有结果；找到就直接采纳，不发第二次写入；找不到才重试。
3. 调用方**不持有**任何自然键时（即丢失的是"创建内容本身"那一步的响应），进入**产品可见的"结果不确定"**状态，要求人工确认，**不允许静默重试**。**Superseded by L1（#119，2026-09-23）**：实测表明"不持有自然键"要收窄为"**没有在内容里写入唯一标记，或标记不唯一**"——创建内容时把调用方自带的唯一标记写进标题，再按「标记 + 作者 + 创建时间窗」对账，两条查询路径都能唯一认出刚创建的对象（实验 2）；标记不唯一时不可判定（实验 1 实测同参数两次创建得到两条对象，计数 2）。因此第 3 条不是"创建内容这一步的默认归宿"，而是"标记不可用时的归宿"。

## Why

- E1-3 实验 3 §4.1 实测：参数完全相同的两次 `addProjectV2ItemById` 返回同一条成员关系，`item.id`、`createdAt`、`updatedAt` 逐字段相同；§4.2 清理后的实测计数为 1，"重复执行'加入 project'的实测计数是 1，不是 2"。因此"先对账、找不到再重试"在这一步是安全的。
- E1-3 实验 3 §4.4 实测自然键候选：`content_id`（issue / change request 的 node id）稳定可重查；`(repo, number) → node id` 稳定；`(project, content)` 由平台保证唯一；而 issue **标题不是**自然键——宽泛关键词 `fixture` 命中 5 条（`total_count = 5`），且标题是可编辑属性。
- E1-3 实验 3 §4.3 实测 `contentId` 的接受范围：issue 与 change request 的 node id 通过、draft 报 `VALIDATION`、不存在的 id 报 `NOT_FOUND`——"拿一个猜出来的 id 去问平台"这条路在平台上没有可用的判定。
- 结论："结果不确定"不能被消除为内部状态：在没有自然键的那一步，平台不提供可对账的输入，静默重试会产生无法检测的重复。**Superseded by L1（#119，2026-09-23）**：该结论句的前半被实验 2 证伪——**平台侧**确实没有"创建内容"的幂等键输入，但**调用方自带**的唯一标记 + 作者 + 创建时间窗可以完成对账（两条路径各唯一命中 1 条；仓库侧列表 ≈0 s、搜索索引 ≈9 s）。实测结论是：**调用方自带的唯一标记 + 作者 + 时间窗可对账；标记不唯一时不可判定**（实验 1 计数 2）。后半句（静默重试会产生无法检测的重复）仍成立且有直接证据：平台不对内容创建去重，同参数两次 `createIssue` 实测得到 2 条对象。

## Rejected

- **响应丢失后直接重试**：在没有自然键的那一步会制造无法检测的重复；有自然键的那一步则应先对账，重试只是对账失败后的动作。
- **用标题当幂等键**：标题不唯一且可变（E1-3 实验 3 §4.4）。
- **把"结果不确定"做成内部重试状态、对用户不可见**：用户无从判断外部是否已经创建了对象，恢复责任无处归属。
- **给"创建内容"步骤加平台侧的幂等键**：平台没有这样的输入（E1-3 实验 3 §4.3 的接受范围与 E1-3 实验 1 §4.5 的输入类型列表都没有幂等键参数）。

## Consequences

- 需要 `pending_external_write` 表，键为 `idempotency_key`（挂接步骤取 `content_id`）；存在未决行时不得发起第二次外部写。
- 状态机需要至少三个可区分的**获知方式**：已确认、通过对账采纳、结果不确定（产品可见）——**订正 2026-09-24（评审响应）**：这三者在结果轴上不是三个取值（前两者同为 `saved`），它们是获知方式轴上的区分，见 `docs/architecture/gate-e1-uncertain-create.md` §2。"结果不确定"必须有面向用户的呈现路径，而不是只写日志。**产品可见的判据（2026-09-24 评审响应）**：「结果不确定」的呈现以「**对账窗口结束后仍未给出唯一结论**」为条件（窗口值见 L1 记录 §3 第 1 条，保持开口）；"写入已发起、尚未对账"是同一行的前段，不得单独触发人工确认——否则实验 2 里 ≈9 s 自愈的写入会在对账完成前就被呈现为"需要人工确认"。
- **证据边界**（**Superseded by L1（#119，2026-09-23）**：原文写"E1-3 实验 3 §8 自述'创建内容那一步响应丢失'这一分支没有实测"，因此本 ADR 第 3 条是推导结论、状态集不得冻结；该分支已由 `docs/architecture/gate-e1-uncertain-create.md` 实验 1–4 补测，状态集有出处，原文保留以记录当时的证据边界）：现在的边界是两条——① 对账窗口的边界值只有两个 n = 1 的样本（搜索索引 ≈9 s、project 条目连接 ≈4 s），"窗口取多少秒"没有证据；② "创建内容"这一步的 `pending_external_write` **键形状**没有观测支持（只能确定不能取 `content_id`，也不能取不唯一的标题）。**状态（2026-09-24 评审响应）**：状态列的**类型**是 `packages/domain` 的 `WriteState`（结果轴，枚举的单一权威）；L1 的观测支持的是**获知方式**四个标注 `confirmed` / `reconciled` / `rejected` / `unresolved` 及其到结果轴的映射（见裁决 §4 的 R8 与 L1 记录 §2）——原文把两轴写成一个 4 值集合，见 L1 记录 §2 的订正说明；残余边界见 L1 记录 §3。
- 本 ADR 不依赖任何 provider 特例：自然键来自调用方输入，对账来自集合读取，两者都是能力契约层可表达的动作。
