# ADR-0004：结果不确定的外部创建先对账再重试；没有自然键时它是产品可见状态

> 状态：Proposed
> 日期：2026-09-21
> 来源：`docs/exec-plan/completed/2026-09-21-gate-e1-ruling.md`（Batch 1，issue #25）；证据见 `docs/architecture/gate-e1-write-and-events.md`（E1-3 / #24）

## Decision

1. 任何外部创建/挂接写入在发起前，把**不依赖响应的自然键**持久化到 `pending_external_write`；对"把既有内容加入项目"这一步，幂等键是 `(project, content_id)`，其中 `content_id` 是发起方本来就持有的输入。
2. 响应丢失时**先对账**：重读条目集合，按自然键查找既有结果；找到就直接采纳，不发第二次写入；找不到才重试。
3. 调用方**不持有**任何自然键时（即丢失的是"创建内容本身"那一步的响应），进入**产品可见的"结果不确定"**状态，要求人工确认，**不允许静默重试**。

## Why

- E1-3 实验 3 §4.1 实测：参数完全相同的两次 `addProjectV2ItemById` 返回同一条成员关系，`item.id`、`createdAt`、`updatedAt` 逐字段相同；§4.2 清理后的实测计数为 1，"重复执行'加入 project'的实测计数是 1，不是 2"。因此"先对账、找不到再重试"在这一步是安全的。
- E1-3 实验 3 §4.4 实测自然键候选：`content_id`（issue / change request 的 node id）稳定可重查；`(repo, number) → node id` 稳定；`(project, content)` 由平台保证唯一；而 issue **标题不是**自然键——宽泛关键词 `fixture` 命中 5 条（`total_count = 5`），且标题是可编辑属性。
- E1-3 实验 3 §4.3 实测 `contentId` 的接受范围：issue 与 change request 的 node id 通过、draft 报 `VALIDATION`、不存在的 id 报 `NOT_FOUND`——"拿一个猜出来的 id 去问平台"这条路在平台上没有可用的判定。
- 结论："结果不确定"不能被消除为内部状态：在没有自然键的那一步，平台不提供可对账的输入，静默重试会产生无法检测的重复。

## Rejected

- **响应丢失后直接重试**：在没有自然键的那一步会制造无法检测的重复；有自然键的那一步则应先对账，重试只是对账失败后的动作。
- **用标题当幂等键**：标题不唯一且可变（E1-3 实验 3 §4.4）。
- **把"结果不确定"做成内部重试状态、对用户不可见**：用户无从判断外部是否已经创建了对象，恢复责任无处归属。
- **给"创建内容"步骤加平台侧的幂等键**：平台没有这样的输入（E1-3 实验 3 §4.3 的接受范围与 E1-3 实验 1 §4.5 的输入类型列表都没有幂等键参数）。

## Consequences

- 需要 `pending_external_write` 表，键为 `idempotency_key`（挂接步骤取 `content_id`）；存在未决行时不得发起第二次外部写。
- 状态机需要至少三个可区分的结果：已确认、通过对账采纳、结果不确定（产品可见）；"结果不确定"必须有面向用户的呈现路径，而不是只写日志。
- **证据边界**：E1-3 实验 3 §8 自述"'创建内容那一步响应丢失'这一分支没有实测"。因此本 ADR 的第 3 条在平台证据上是推导结论；在补上该观测之前，`pending_external_write` 的状态机取值集合不得冻结（见 `docs/architecture/gate-e1-ruling.md` §4 的 R8 与 §8 第 1 条）。
- 本 ADR 不依赖任何 provider 特例：自然键来自调用方输入，对账来自集合读取，两者都是能力契约层可表达的动作。
